# App Games 将来構想・未実装計画

> この文書は、未実装、検討中、段階導入中の構想を記録する。
> ここに書かれた内容を、現在利用できる機能として扱わない。
> 現在の実装は [`CURRENT_STATE.md`](./CURRENT_STATE.md) とコードを確認する。

## 文書の扱い

各項目には、実装着手時に次の状態を付ける。

- `構想`: 方針のみで、実装時期未定
- `設計中`: 仕様・影響範囲を整理中
- `実装中`: コード変更中だが完了条件未達
- `検証中`: 実装済みでE2E・運用確認待ち
- `現行へ移管`: 実装と検証が完了し、`CURRENT_STATE.md` へ移したもの

完了した項目はこの文書に残し続けず、現行文書へ移管する。

## プラットフォーム構想

状態: `構想 / 設計中`

Game Fieldsを次の層へ発展させる。

1. 本番ゲームプラットフォーム
2. 共通ゲーム基盤
3. 外部制作者がゲームを制作・検証・提出できるSDK
4. SDKゲームを審査して本番へ採用する昇格導線
5. 開発環境で作ったゲームを本番へ移す別系統の導線

詳細は [`PLATFORM_VISION.md`](./PLATFORM_VISION.md) とSDK関連資料を参照する。

## SDKと外部ゲームパッケージ

状態: `設計中 / 実装中`

- 制作者はゲーム固有部分を中心に作成し、ルーム、ログイン、観戦、時間管理、デバッグなどは共通基盤を利用する
- SDKから開発環境への昇格と、SDKから本番への正式採用を分離する
- `dev → main` は本体開発用の別導線として保持する
- SDKクライアント製作者向けの管理UIを整備する
- 共通モジュールの必須、解除可能、任意を管理できるようにする
- パッケージの互換性、保持、削除、バージョン管理を明示する

## LLM基盤の将来変更

状態: `構想 / 段階導入`

- 招待・テストパスワードによるGame Fields API利用を、購入権またはクレジット権限へ置き換える
- フィードバック検索をRedisタグ検索からembeddings / vector searchへ段階的に移行する
- 既存のUI、生成メタデータ、プロバイダーゲートウェイを維持したまま検索基盤だけを交換できる構造にする
- 利用量、課金元、失敗理由を管理画面と観測基盤で追跡しやすくする

## 広告

状態: `構想`

広告枠コンポーネントは存在するが、本番広告配信は未実装。

本番化前に必要なもの:

- 同意取得フロー
- 広告プロバイダーアダプター
- CSP設計
- プライバシーポリシーと利用規約の確認
- active playとdebug roomには表示しないことの自動監査
- 表示位置、非表示設定、課金プランとの関係整理

## WebSocket本番利用

状態: `検討中`

現在はPreview・ローカル開発中心。正式有効化前に次を確認する。

- 本番負荷と接続上限

## 構想を実装へ移す条件

構想を「実装済み」と扱うには、少なくとも次を完了する。

1. 影響範囲を列挙する
2. 既存コードへのバックフィル対象を洗い出す
3. コードと設定を変更する
4. lint / test / buildを通す
5. 必要なE2Eと実機確認を行う
6. 環境変数・DB・Vercel Projectなどの台帳を更新する
7. `CURRENT_STATE.md` と関連正本へ反映する
8. この文書から完了済み記述を削除または履歴化する
